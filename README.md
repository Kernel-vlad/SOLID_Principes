# SOLID Principles in C#

Даний проєкт містить практичні приклади застосування **SOLID** принципів об'єктно-орієнтованого дизайну на мові C#. 

SOLID — це акронім, що об'єднує 5 основних принципів розробки ПЗ для створення гнучких, масштабованих та легко підтримуваних систем.

---

## 🚀 Навіщо використовувати SOLID?

- **Зменшення зв'язаності (Low Coupling)** та **висока зв'язаність функціоналу (High Cohesion)**[cite: 1].
- **Повторне використання коду** та простіше написання модульних тестів (Unit Tests)[cite: 1].
- **Стійкість до змін:** додавання нових фіч не ламає існуючу логіку[cite: 1].

---

## 📌 Огляд принципів та прикладів

### 1. S — Single Responsibility Principle (SRP)
> **Принцип єдиної відповідальності:** Клас повинен мати лише одну причину для зміни.

Всі обов'язки розділені між вузькоспеціалізованими класами:
- `Employee` — зберігає дані співробітника.
- `SalaryCalculator` — розраховує зарплату.
- `EmployeeRepository` — відповідає за збереження даних у БД.
- `EmployeeReportService` — відповідає за генерацію звітів.

---

### 2. O — Open/Closed Principle (OCP)
> **Принцип відкритості/закритості:** Програмні сутності мають бути відкритими для розширення, але закритими для змін.

Клас `AreaCalculator` обчислює площу через абстрактний клас `Shape`. Для додавання нової фігури (`Circle`, `Rectangles`, `Triangle`) достатньо успадкувати `Shape` — код розрахунку змінювати не потрібно.

---

### 3. L — Liskov Substitution Principle (LSP)
> **Принцип підстановки Барбари Лісков:** Об'єкти дочірніх класів повинні замінювати об'єкти базових класів без порушення роботи програми.

Класи `Rectangle` та `Square` реалізують спільний інтерфейс `IShape`, забезпечуючи коректний розрахунок площі без створення непередбачуваної поведінки перевизначення `Width` / `Height`.

---

### 4. I — Interface Segregation Principle (ISP)
> **Принцип розділення інтерфейсів:** Клієнти не повинні залежати від інтерфейсів, які вони не використовують.

Великий інтерфейс розділено на два вузькі: `IWorkable` та `IEat`.
- `HumanWorker` реалізує обидва інтерфейси (`IWorkable`, `IEat`).
- `RobotWorker` реалізує лише `IWorkable` (роботу не потрібно їсти).

---

### 5. D — Dependency Inversion Principle (DIP)
> **Принцип інверсії залежностей:** Модулі вищого рівня не повинні залежати від модулів нижчого рівня. Обидва повинні залежати від абстракцій.

Сервіс `NotificationService` залежить від абстракції `IMessageSender`, а не від конкретних реалізацій (`EmailSender` чи `SmsSender`). Залежність передається через конструктор (**Dependency Injection**).
